## Personal Finance Manager

Консольное приложение для учета личных финансов на Java 21. Разработано в рамках итогового задания по ООП в МИФИ.

Приложение позволяет вести доходы и расходы, настраивать бюджеты по категориям, получать отчеты и переводить средства
другим пользователям. Данные сохраняются в JSON-файл между запусками.

### Возможности

- Регистрация пользователей и вход по логину и паролю.
- Отдельный кошелек, категории и бюджеты для каждого пользователя.
- Учет доходов и расходов по категориям.
- Создание и переименование категорий без потери истории операций.
- Установка и изменение бюджетов, контроль расходов по категориям.
- Предупреждения при использовании 80% бюджета, превышении лимита, нулевом и отрицательном балансе.
- Просмотр баланса, общей статистики и отчетов по выбранным категориям.
- Переводы между пользователями.
- Сохранение данных в JSON и экспорт транзакций в CSV.

### Технологии

- Java 21
- Maven
- Jackson (JSON)
- JUnit 5
- Checkstyle
- GitHub Actions

### Запуск

Понадобятся JDK 21 и Maven.

Сборка и проверка проекта:

```bash
mvn clean verify
```

Запуск консольного приложения:

```bash
mvn exec:java -Dexec.mainClass=ru.mephi.promoit.wallet.Main
```

После запуска в консоли появится приглашение `finance>`. Список команд доступен по `help`.

### Пример работы

Ниже приведен пример работы с приложением, охватывающий основные возможности CLI.

#### Регистрация и авторизация

```text
finance> register alex password123
User registered: alex

finance> register bob password123
User registered: bob

finance> login alex password123
Logged in as alex
```

#### Категории, доходы и расходы

Создадим категории для доходов и расходов, затем добавим несколько операций.

```text
finance> category add income Salary
Category created: Salary (INCOME)

finance> category add income Bonus
Category created: Bonus (INCOME)

finance> category add expense Food
Category created: Food (EXPENSE)

finance> category add expense Transport
Category created: Transport (EXPENSE)

finance> income add Salary 10000
Income added: 10000

finance> income add Bonus 2000
Income added: 2000

finance> expense add Food 1500
Expense added: 1500

finance> expense add Transport 500
Expense added: 500

finance> balance
Current balance: 10000
```

#### Бюджеты и предупреждения

Установим бюджет на питание и добавим расход, при котором будет достигнуто 80% лимита.

```text
finance> budget set Food 4000
Budget set: Food = 4000

finance> expense add Food 1700
Expense added: 1700
Warning: 80% or more of Food budget used

finance> budget list
Category                  Limit        Spent    Remaining
Food                       4000         3200          800
```

Лимит можно изменить повторной командой `budget set`.

```text
finance> budget set Food 5000
Budget set: Food = 5000
```

#### Переименование категорий

Категорию можно переименовать без потери истории операций и настроенного бюджета.

```text
finance> category rename expense Food Groceries
Category renamed: Food -> Groceries

finance> category list
INCOME:
  Salary
  Bonus
EXPENSE:
  Groceries
  Transport
```

Все существующие транзакции и бюджеты продолжают ссылаться на прежний UUID категории.

#### Отчеты

Общая статистика доступна через команду `summary`.

```text
finance> summary
```

Для получения отчетов по отдельным категориям или нескольким выбранным категориям используются команды `report`.

```text
finance> report expense Groceries
Category             Amount
Groceries            3200
Total                3200

finance> report expense Groceries Transport
Category             Amount
Groceries            3200
Transport             500
Total                3700

finance> report income Salary Bonus
Category             Amount
Salary              10000
Bonus                2000
Total               12000
```

#### Переводы между пользователями

Переведем 1500 другому зарегистрированному пользователю.

```text
finance> transfer bob 1500
Transfer completed: 1500 to bob

finance> balance
Current balance: 6800

finance> logout
Logged out

finance> login bob password123
Logged in as bob

finance> balance
Current balance: 1500

finance> category list
INCOME:
  TransferIn
```

Перевод создает две связанные транзакции: расход у отправителя и доход у получателя. Обе операции имеют общий `transferId`.

#### Экспорт в CSV

Каждый пользователь может экспортировать операции собственного кошелька.

```text
finance> export csv transactions.csv
Exported 1 transactions to transactions.csv
```

CSV содержит идентификатор транзакции, тип операции, категорию, сумму, время создания и идентификатор перевода.

#### Сохранение данных

При штатном завершении приложения данные пользователей, транзакции, категории и бюджеты сохраняются в `wallet-data.json`.

```text
finance> exit
Goodbye!
```

При следующем запуске данные загружаются автоматически. После авторизации пользователь продолжает работу со своим кошельком.

Полный список доступных команд можно посмотреть через `help`.

### Архитектура

Приложение разделено на несколько слоев. Консольный интерфейс отвечает за ввод и вывод, сервисы выполняют
бизнес-операции, доменная модель хранит состояние финансов, а репозитории и компоненты persistence отвечают за работу с
данными.

```text
src/main/java/ru/mephi/promoit/wallet/
├── Main.java                 # создание и связывание компонентов
├── cli/
│   ├── ConsoleApplication.java
│   ├── command/             # типизированные команды
│   ├── parser/              # разбор пользовательского ввода
│   └── executor/            # выполнение команд и вывод результатов
├── domain/
│   ├── model/               # User, Wallet, Transaction, Category, Budget
│   └── service/             # финансовые операции и бизнес-правила
├── repository/              # хранение данных в памяти
├── persistence/
│   ├── dto/                 # структуры данных для JSON
│   ├── JsonPersistenceService.java
│   └── CsvExportService.java
└── security/                # хеширование паролей
```

#### Обработка команд

Ввод обрабатывается по цепочке:

```text
ConsoleApplication
        │
        ▼
   CommandParser ──► CommandGroupParser
        │             (Auth, Budget, Category, ...)
        ▼
   FinanceCommand
        │
        ▼
   CommandExecutor
        │
        ▼
   Domain services ──► Repositories / Wallet
```

Для команд используется **паттерн Command**. Каждая операция представлена отдельным `record`, реализующим
`sealed interface FinanceCommand`: например, `AddExpenseCommand`, `SetBudgetCommand` или `TransferCommand`. Парсер
создает объект команды, а `CommandExecutor` выполняет соответствующее действие. Таким образом, разбор строки отделен от
бизнес-логики.

Для разбора групп команд применяется подход, близкий к **Strategy**: интерфейс `CommandGroupParser` реализуют
специализированные парсеры (`AuthCommandParser`, `CategoryCommandParser`, `BudgetCommandParser` и другие).
`CommandParser` выбирает нужную реализацию по первому слову команды. Это позволяет добавлять новые группы команд без
расширения одного большого парсера.

#### Сервисы и зависимости

Бизнес-логика сосредоточена в сервисах:

- `AuthService` — регистрация, вход и текущий пользователь;
- `FinanceService` — доходы, расходы и категории;
- `BudgetService` — лимиты, остатки и предупреждения;
- `StatisticsService` — общая статистика и отчеты;
- `TransferService` — переводы между пользователями;
- `UserFinanceService` — доступ к финансовым данным авторизованного пользователя.

Используется **Service Layer**: сервисы не читают команды из консоли и не форматируют таблицы для вывода. Зависимости
передаются через конструкторы (**constructor injection**), а их создание сосредоточено в `Main`. Контейнер внедрения
зависимостей не используется — для небольшого приложения достаточно ручной сборки объектов.

Классы `UserRepository`, `UserFinanceRepository`, `CategoryCatalog` и `BudgetCatalog` реализуют **Repository-подобный
подход** к хранению данных в памяти. Они скрывают операции поиска, добавления и восстановления сущностей. Это конкретные
реализации, без отдельного набора интерфейсов репозиториев.

#### Доменная модель

`UserFinance` объединяет три независимые части финансов пользователя: `Wallet`, `CategoryCatalog` и `BudgetCatalog`. Для
каждого пользователя создается собственный набор этих объектов.

**Баланс вычисляется из транзакций.** `Wallet` хранит список операций, а `getBalance()` суммирует доходы и вычитает
расходы. Отдельное изменяемое поле баланса не используется, поэтому оно не может разойтись с историей операций.
`getTransactions()` возвращает неизменяемую копию списка.

Для денежных значений используется `BigDecimal`, а для идентификаторов — `UUID`. `Transaction` и `Category` оформлены
как `record` с проверкой обязательных полей. При переименовании категории создается новый объект с прежним UUID.
Поскольку транзакции и бюджеты ссылаются на UUID, история расходов и установленные лимиты сохраняются без изменений.

Обычные расходы допускают отрицательный баланс, но сопровождаются предупреждением. Для перевода средств, напротив,
проверяется достаточность остатка.

#### Переводы между пользователями

`TransferService` создает две операции: расход у отправителя (`TransferOut`) и доход у получателя (`TransferIn`). У
каждой операции собственный UUID, но общий `transferId`, по которому можно связать обе стороны перевода.

Метод `transfer()` объявлен `synchronized`: это ограничивает одновременное выполнение переводов через один экземпляр
сервиса. **Полной потокобезопасности приложения это не гарантирует**, поскольку остальные операции с кошельками отдельно
не синхронизированы. Приложение рассчитано прежде всего на последовательную работу через CLI.

В общей статистике переводы учитываются как доходы и расходы соответствующих пользователей.

#### Сохранение и восстановление

В рабочем состоянии данные находятся в памяти. Для сохранения используется **DTO-подход**: `ApplicationData`, `UserData`
и `UserFinanceData` задают структуру JSON отдельно от внутренних классов приложения. Сериализация выполняется Jackson.

При запуске `JsonPersistenceService` восстанавливает пользователей, категории, бюджеты и транзакции, проверяя
корректность данных и связей. При штатном завершении приложение записывает JSON во временный файл, затем заменяет
основной файл с помощью атомарного перемещения, если файловая система его поддерживает. Это снижает риск повреждения
данных при записи, но не заменяет полноценную транзакционную систему хранения.

Пароли хранятся не в открытом виде, а в виде хешей, полученных с использованием PBKDF2.

#### Что сознательно оставлено за рамками

Это локальное учебное приложение: без базы данных, веб-интерфейса и фоновой обработки. CSV поддерживает только экспорт.
Команды разбиваются по пробелам, поэтому имена категорий и пути с пробелами не предусмотрены. Сохранение выполняется при
штатном выходе, а не после каждой операции.

### Хранение данных

При запуске приложение загружает данные из `wallet-data.json` в текущем рабочем каталоге. При завершении работы данные
сохраняются в этот же файл. Для записи используется временный файл с последующей заменой основного.

Экспорт CSV выполняется командой `export csv <file>` и включает только транзакции текущего пользователя. Импорт CSV не
предусмотрен.

Файл `wallet-data.json` содержит пользовательские данные, поэтому его не следует добавлять в Git.

### Тестирование и CI

Запуск тестов:

```bash
mvn test
```

Полная проверка, включая Checkstyle:

```bash
mvn clean verify
```

Отдельный запуск Checkstyle:

```bash
mvn checkstyle:check
```

GitHub Actions запускает `mvn -B clean verify` при `push` и `pull_request`. Тесты покрывают сервисы, работу команд CLI,
переводы, сохранение данных и экспорт CSV.
